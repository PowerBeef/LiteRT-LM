## Terms (for glossary.md)

| term | meaning | prefer / avoid |
| --- | --- | --- |
| C API version | The semantic version of LiteRT-LM's C interface (`LITERT_LM_C_API_VERSION_*`, `C_API_VERSION` in `version.bzl`), separate from the runtime version: 0.2.0 in v0.18.0, 1.0.0 in agello-next | prefer "C API 1.0.0"; avoid calling it the LiteRT-LM version |
| `LiteRtLmStatusCode` | The C return type: the 17 canonical status codes, 0 = OK | prefer "status code" |
| last error | The thread-local message of the most recent failed C call on a thread | avoid "errno" except as an analogy |
| out-parameter | A trailing `out_*` pointer through which a C function returns its result (C API 1.0.0) | |
| stream chunk | A `LiteRtLmStreamChunk`: text, final flag, error; valid only during the callback | |
| final chunk | The chunk with `is_final` true; the last callback of a stream, delivered on the callback thread | |
| execution thread / callback thread | The two single-thread pools of `ThreadedExecutionManager` | prefer these names over "worker thread" |
| session API / conversation API | The two C generation layers: plain inputs and text out vs JSON messages with templates, tools and constraints | |
| shipped wrapper | The Swift package at `agello` `85b1a776` (v0.18.0 + two Swift patches) that Agello vendors | avoid "Agello's fork" for it |
| `StreamContext` | The Swift object passed as `callback_data` that bridges C callbacks to an `AsyncThrowingStream` | |
| automatic tool calling | The Swift wrapper running tool calls itself and sending their responses back, up to 25 rounds | |
| response format | A per-message constraint (JSON schema or regex) in Swift; needs `enableResponseFormat` | prefer over "structured output" when naming the API |
| experimental flags | Process-wide `ExperimentalFlags` static vars, settable after opting in | |
| poisoned session | A session after `CancelProcess`, which upstream says must not be reused | |

## Notes for other pages

- **engine-and-sessions.md (lm-engine):** `ThreadedExecutionManager` has one execution and one callback thread; partial stream callbacks run on the execution thread inside `Tasks::Decode`; the final callback runs on the callback thread and the execution thread waits up to 10 s for it; v0.18.0 is the same (LM-CAPI-028, LM-CAPI-050). `SessionAdvanced::~SessionAdvanced` waits up to 10 minutes without cancelling; a task leaves `active_tasks` only in an end state, and `kLastCallbackQueued` is not one (LM-CAPI-048). Upstream's note that a session is poisoned after `CancelProcess` (LM-CAPI-030). Our telemetry comment in the destructor (`sa_dtor`) is ours.
- **conversation.md (lm-conversation):** the C layer's conversation creation silently drops invalid initial messages, tools and extra context (LM-CAPI-020); system message text that isn't JSON is used as a string (LM-CAPI-019); cancellation reaches the user callback as `CancelledError("Task cancelled")` (LM-CAPI-049); builder defaults (LM-CAPI-023). Swift streams run tools regardless of `automaticToolCalling` (LM-SWIFT-017); response formats skip user messages when tools are registered with automatic calling (LM-SWIFT-031); thinking config only on the first tool round (LM-SWIFT-012).
- **troubleshooting.md:** `LiteRTLMError.conversation(.invalidResponse("CANCELLED: Task cancelled"))` after `cancel()` (LM-SWIFT-022); session streams report the token limit as an error string (LM-CAPI-026); the 10-minute stall and its fix (LM-SWIFT-020); `benchmarkNotEnabled` vs `benchmarkInfoUnavailable`; long embedding inputs fail from Swift (LM-SWIFT-042); `fatalError` in `@ToolParam` (LM-SWIFT-026).
