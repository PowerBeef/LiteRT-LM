## Terms (for glossary.md)

| term | meaning | prefer / avoid |
| --- | --- | --- |
| Environment | LiteRT's `LiteRtEnvironmentT`: options, accelerator registry, buffer-handler registry, GPU environment; one per LiteRT-LM engine | Prefer "LiteRT environment"; avoid "context" |
| Accelerator | A registered `LiteRtAcceleratorDef` that creates one TFLite delegate per compiled model ("GPU Metal", "CpuAccelerator") | Prefer "accelerator" for the registry entry and "delegate" for what it creates |
| GPU Metal accelerator | LiteRT's ML Drift Metal accelerator (`ml_drift_metal_accelerator`), statically linked in our build | Avoid "Metal delegate" for the accelerator itself |
| Static GPU accelerator | The accelerator linked into the binary that registers itself through `LiteRtStaticLinkedAcceleratorGpuDef` | Avoid "built-in GPU" |
| Auto-registration | Registration of NPU, WebNN, GPU and CPU accelerators, in that order, at environment creation | |
| Compiled model | `LiteRtCompiledModelT`/`CompiledModel`: a TFLite interpreter plus delegates for one hardware set | Prefer over "interpreter" |
| Hardware set | The `LiteRtHwAcceleratorSet` passed to compilation (CPU, GPU, NPU bits) | Prefer over "backend" when talking about LiteRT (backend is LiteRT-LM's term) |
| Active subgraph | A subgraph that delegates are applied to: all, or the roots of the selected signatures | |
| CPU tensor | A tensor read or written by an undelegated or XNNPACK/YNNPACK node; gets host-memory requirements | |
| Partition | A delegate node that replaced a group of TFLite nodes | Prefer over "cluster" |
| Delegation metrics | Per-accelerator counts of delegated nodes and partitions recorded at compile time | |
| Magic number | A prime placeholder dimension (32003) rewritten to a real size at load | Prefer "magic number (placeholder)"; avoid "dynamic shape" |
| Tensor buffer | `LiteRtTensorBufferT`: a reference-counted, lockable buffer of one type, with an optional event | |
| Buffer requirements | Supported buffer types (first preferred), size, alignment and strides for a tensor | |
| Custom tensor buffer handlers | Per-type create/lock/unlock/clear/import functions registered by an accelerator | |
| Host shadow | The host copy the Metal buffer handler keeps for a locked Metal tensor | Avoid "mapping" or "zero-copy" for Metal locks |
| Zero-copy registration | Binding a buffer whose type the delegate accepts, without a runtime copy | Only for `RegisterBuffer`; not for host locks of GPU buffers |
| Post-dispatch event | The completion event a GPU backend can attach to outputs of an async run; the Metal backend provides none in practice | |
| Kernel mode | CPU option: delegate (XNNPACK), reference or builtin TFLite kernels | |
| XNNPACK weight cache | A file (or `:memory`) of XNNPACK-packed weights reused across loads | Distinct from ML Drift's weight cache |
| KleidiAI | Arm's micro-kernel library XNNPACK uses on Arm64 | Avoid calling it a delegate |
| Dequant-BMM rewrite | XNNPACK's rewrite of `dequantize(INT8) → batch matmul` into `convert(qint8 → qcint8) → batch matmul` | |
| Delegate clustering | TFLite's reordering to reduce switches between delegated and undelegated nodes; off for Gemma 4 | |
| Composite inlining | Replacing StableHLO composites with their decompositions when the runtime options exist (LiteRT-LM's CPU path) | |
| Runtime proxy | `RuntimeProxy`, the function table through which the C++ API calls the C API | |

## Contradictions

None assigned. New findings, each resolved in the page that owns it:

- **NEW-1 (XNNPACK fix date).** Agello's notes and our commit `b8f807ec` date upstream XNNPACK's fix `c72e2a4a` 2026-09-23; the commit's author date is 2026-09-22 19:37 −0700, which is 2026-09-23 UTC. Both are right; the page states the author date and the UTC day. Claims: RT-CPU-015.
- **NEW-2 ("upstream has the same code").** Our commit `51f099fb`'s message says upstream XNNPACK still had the oversized scale buffer; `b8f807ec` corrected it (upstream fixed it in `c72e2a4a`; TensorFlow's XNNPACK pin `d89ef666` predates the fix). The page follows `b8f807ec` and the WORKSPACE comment. Claims: RT-CPU-012, RT-CPU-015, RT-CPU-016.
- **NEW-3 (AUDIT §2.2, environment options).** AUDIT says the LiteRT environment receives only magic-number options and log severity, "no library dir". At `7b872544` that holds for CPU and GPU backends; NPU backends also get the dispatch and compiler-plugin directories. Claims: RT-RUN-008.
- **NEW-4 (LiteRT cancellation API, upstream candidate).** `compiled_model.h` declares `EnableCancellation()`/`Cancel()` without definitions, and the C header's comment points to `LiteRtEnableCompiledModelCancellation`/`LiteRtCancelCompiledModel`, which do not exist at `362759838`. Only the polling callback works. Claims: RT-RUN-023.
- **NEW-5 (gpu_accelerator flag comment).** `runtime/executor/BUILD` says "macOS uses WebGPU" by default; in our fork `default_static_gpu_accelerator` links the Metal accelerator on macOS without consulting that flag. The comment describes Google's setup, which their v0.18.0 macOS binary follows (it contains "GPU WebGPU", not "GPU Metal"). Claims: RT-RUN-005, RT-OTH-005.
- **NEW-6 (passive Metal waits do not reach Agello).** TELEMETRY.md reports the passive-wait change's CPU saving (2.0 ms instead of 29.3 ms of process CPU per token); our change `645aaf65` applies only when LiteRT-LM is not benchmarking, and Agello sets `ExperimentalFlags.enableBenchmark = true`, so the app requests active (busy) waits in both the documented and the shipped build. No document claims the app gets passive waits, but user-facing or commit text about the saving should say it needs benchmark mode off. Claims: RT-RUN-028.

## Notes for other pages

- **litert/ml-drift-delegate.md (rt-delegate):** the Metal delegate creates the `GpuEnvironment` with a global `MetalDevice` and a new command queue (RT-RUN-009); in async mode the Metal backend returns no post-dispatch event and the kernel returns without waiting or attaching events (RT-RUN-022); Metal lock/unlock semantics and shadow copies (RT-RUN-026); buffer types requested by `GpuBackendMetalLitert` (RT-RUN-060); Agello's benchmark flag forces the active wait (RT-RUN-028).
- **litert-lm/executors.md (lm-executors):** the main graph is compiled GPU-only, so an op ML Drift rejects fails engine creation (RT-RUN-016); decode always uses `RunAsync` (RT-RUN-063); embedding lookups are one CPU model run per token per table, 4,098 for a 2,049-token prompt (RT-CPU-003, RT-CPU-004); magic-number counts in the E4B run (RT-RUN-013).
- **litert-lm/engine-and-sessions.md (lm-engine):** LiteRT serializes compiled-model creation and environment creation with process-wide mutexes, so two engines loading at once take turns (RT-RUN-014); environment options LiteRT-LM passes (RT-RUN-008).
- **litert-lm/swift-api.md (lm-api):** `Backend.cpu(threadCount:)` is ignored by `Engine` in both wrappers (RT-CPU-007); `ExperimentalFlags.enableBenchmark` changes the GPU wait type (RT-RUN-028).
- **litert-lm/file-format.md (lm-components):** file-backed LiteRT loading is NPU-only because magic numbers are rewritten in place (RT-RUN-011); the mapping is `MAP_PRIVATE` with `PROT_WRITE`, and `MADV_DONTNEED` on Apple (RT-RUN-038). `generated/models/*` could not parse the per-layer embedder section (its op count, 49, comes from the engine log).
- **litert-lm/build-and-release.md, versions.md (lm-build):** what `--config=agello` sets and where the Metal accelerator link comes from (RT-RUN-005, RT-RUN-069); XNNPACK pin and patch (RT-CPU-016); YNNPACK only on linux_arm64 (RT-CPU-029, RT-OTH-007); KleidiAI in both binaries (RT-CPU-010, RT-CPU-011); Google's macOS binary uses the WebGPU accelerator (RT-OTH-005).
- **memory.md:** the unpatched XNNPACK scale arrays (RT-CPU-013, RT-CPU-014) and the post-fix iPhone footprint (RT-CPU-017); embedding lookups touch only the rows used (RT-CPU-020); Metal locks allocate a host shadow of the tensor's packed size per locked buffer (RT-RUN-026).
- **troubleshooting.md:** "Failed to create OpenCL context." is benign on Apple (RT-RUN-010); "Some ops are not accelerated" (RT-RUN-015); audio backend constraint mismatch (RT-CPU-023); YNNPACK requested in a build without it fails CPU compilation (see runtime.md, Limits and failure modes).
- **apple-platform.md:** Apple platform macros (RT-RUN-027); the Metal accelerator in both iOS binaries (RT-RUN-029); Google's macOS build runs ML Drift over Dawn (RT-OTH-005).
- **models/gemma4-e4b.md:** which E4B sections run on the CPU and why (RT-CPU-001, RT-CPU-022, RT-CPU-023), and the XNNPACK op coverage of the E4B graphs (RT-CPU-021).
